# Progressive writer handoff

Follow the [writer guide](writer-guide.md) for grow-me's HTML format and project-requirement-writer for additional writing guidance when installed. For a **new** document, use `assets/writer-shell.html`. For an existing maintained task page, preserve the page and its history. Use a validated preview sibling for early reading and atomically update the original page for final delivery.

## Prepare rules before offering save

During question drafting, use answers and existing context only. Put unverified facts on a pending-verification list. While the user is answering the expected final round, use the heartbeat-protected, timed `work.mjs --final-round -- <command>` entry described in [runtime](runtime.md#集中查代码) to investigate code, resolve that list, and prepare chapter structure. Before `offer`, read the bundled writer guide, this handoff, the shell structure and the installed project-requirement-writer if present. After save, claim and write directly from the frozen answers. If preparation was interrupted, name the facts that still need checking. Use the frozen decision when it differs from the prepared content.

Every newly authored question, including first-round roots, supplies optional-v2 `chapter_id`: the root question ID (a root names itself). Other questions name a root reachable through their dependencies. This document membership does not change `depends_on`, review or tree geometry. Old v2 questions without the field retain the original primary-root projection; v1 is unchanged and read-only. `/context` exposes the resolved ID, and frozen `/document/status.source.chapters[].node_ids` gives the exact membership for writing. Use explicit assignments directly, rather than reverse-engineering chapter membership at save time.

## Write and publish one chapter at a time

After the user saves or retries, get the current `job_id` from `check.mjs` (`document.job_id`) or `GET /document/status` (`job_id`). Use it to claim while the phase is `requested`, then save `/document/status` in the workspace as `status.json`. Share a short ID contract among the three views: the same requirement IDs, work/criterion IDs, dependencies, chapter anchors and confirmed decisions. These are transient generation inputs; tree.json remains the only interview state. Avoid reprinting full tree/history or template code in every task.

Each part is a UTF-8 JSON file in a workspace generation directory:

```json
{
  "source": {"session_id":"from status", "revision":6, "digest":"from status", "job_id":"from status"},
  "view":"chapter",
  "chapter_id":"root node id",
  "title":"A readable topic name",
  "html":"<p class=\"chapter-conclusion\">一句话说清这个主题的结论。</p>"
}
```

- One `view:chapter` per root, generated by `render-chapter.mjs` below. The assembler supplies its exact anchor and readiness flag. AI writes the explanation and descriptive links. The script supplies the interview transcript.
- One `view:design` with the remaining requirement and constraint HTML. Optional plain text fields are `title`, `summary`, `updated`, `position` and `next`. Write actual progress and the next action. Add author-supplied pending items in `open_questions`, each with `id`, `text`, `origin` and optional `chapter_id`. The assembler counts these items and the frozen pending questions.
- One `view:plan` with numbered work cards, their prerequisites, visible outcomes, irreversible actions and named links to related definitions. See the [HTML work card example](writer-guide.md#one-html-three-views).
- One `view:acceptance` with four-cell criterion rows. Put the canonical value in `data-status` and show the Chinese status label. See the [HTML criterion example](writer-guide.md#one-html-three-views).

The three shared views can be authored independently using the common ID contract. Topic chapters are sequential: write one complete chapter, publish it successfully, then write the next. Use parallel agents only when authorized; parallel assembly support does not itself promise lower model latency or permit batching completed chapters.

检查冻结访谈里的待定答案，按未确认的选择写。用户提前要方案时，把尚未讨论的决定列进「还没定的」，再从相关开发项用名字链接过去。正文用大白话，先结论后细节。链接文字用名字，正文不写编号、英文状态词、会话号或 revision。

Start `check.mjs --heartbeat` before writing and stop that heartbeat at the end. For **each** chapter, write its explanatory HTML outside the parts directory. Start with `<p class="chapter-conclusion">` for the one-sentence conclusion, then use 「你会看到」 and 「为什么」 to explain the observable change and its reason. Use a short chapter name in `--title`.

```text
node <skill>/scripts/render-chapter.mjs --context <status.json> --tree <frozen-tree.json> --chapter <root-id> --title "<章节名>" --explanation <chapter-prose.html> --out <parts-dir/chapter-id.json>
```

The script validates the frozen source and exact chapter membership. It puts each question, actually selected labels, and verbatim notes in a closed 「访谈原话」 at the end of the chapter. Earlier v2 questions without `chapter_id` use their original root mapping. Retry with a new job requires new source-bound parts. State conclusions in the explanation and leave the questions and answers to the script.

Use the generated chapter part as returned. The assembler lists unresolved interview questions once at the start of the design view, labeled 「待定的题」 and linked to the chapter. Refer to each entry from relevant work with `data-questions` and `deferred-<node-id>` for IDs containing only ASCII letters, digits, `_` and `-`. For other IDs or unanswered rephrases, use the generated question ID from the preview. Link to additional `open_questions` by their own IDs. Use the question text as the link label. Cite the confirmed answers each work item relies on with `data-decisions` and the `decided-<node-id>` IDs from the transcript; see the [writer guide](writer-guide.md).

**Mandatory: immediately after each chapter is written, run this command and confirm publication before writing the next chapter. Never accumulate several chapters for a single preview publication.** Keep already published parts in the directory; the new chapter is the only newly published one:

```text
node <skill>/scripts/compose-document.mjs --context <status.json> --tree <tree.json> --parts <parts-dir> --preview --url <local-url>
```

This atomically writes `<document_file>.preview.html`, validates the completed chapters against source/revision/digest/job and publishes each one. Missing views/links are visibly pending in the preview, never passing acceptance. A corresponding fruit becomes readable immediately; other fruit stays labeled “生成中”. Source-stale or duplicate parts fail without replacing the final HTML. Keep only part JSON files in `--parts`. Move host sidecars such as `*.metadata.json` out of the directory if validation flags them. The error names the file and the invalid field. Use distinct part names on case-insensitive filesystems.

`--url` is needed for actual publication: without it the command only writes a local preview and records no publication time. Successful publication returns `newly_published_chapters`, `chapter_timings` and `chapter_timing_file`. The service records the first accepted timestamp per chapter and job; re-publishing a chapter preserves it. Two or more newly published chapters in one invocation emit an explicit warning on stderr (also in successful JSON output), without failing the command. An existing published chapter plus one new chapter is not a batch violation. See [verification](verification.md#逐章发布时间) for the permanent timing log and how to read it.

Use `/document/control` action `progress` with the current expected_session_id/expected_revision/job_id and stage `drafting`, `design`, `plan`, `acceptance` or `checking` as real work starts. The timer is elapsed time, not an estimated percentage. Avoid repeated stage-only calls while nothing changes.

Once all pieces are ready:

```text
node <skill>/scripts/compose-document.mjs --context <status.json> --tree <tree.json> --parts <parts-dir> --url <local-url>
```

For a maintained task page, update the configured HTML in place with current source markers and the same pending-question IDs and text the preview uses. Run the final command with `--existing` in place of `--parts <parts-dir>` to validate that page and export its handoff.

Final assembly checks the source, all views and chapters, then calls `validate-task.mjs` in process. After these checks pass, it publishes the final HTML and atomically writes `task.manifest.json` beside it. The manifest uses the frozen interview topic, session and revision, work dependencies, readable acceptance text with AC IDs, linked pending questions and linked confirmed answers as `decisions`. Unlinked pending items and unlinked confirmed answers go to the first dependency-free pack. A pack without confirmed answers omits `decisions`. Each pack gets `external_effects` from its work item or phase's `data-field="effects"` block. Leave `scope_files` and `tags` empty. Leave out `estimated_files`, `cross_module` and `risk` and skip code investigation for export. A preview never exports the manifest.

Give each item one effects block with one `<li>` per irreversible action it will execute. For example, use `<ul data-field="effects"><li>写线上数据库：执行迁移 add_xxx</li></ul>`. Only list text is exported, in order, with normalized whitespace. Write `<li>无</li>` when there are no actions. Only the standalone `无` is omitted.

Include writes to production or other real databases (including running migrations), deployments or enabling production flags, outbound messages, notifications or emails, paid API calls (including batch calls), and deleting or overwriting user data. Exclude local commits, work against test databases, and code-only changes. If the item writes a migration script and leaves execution for production rollout, record that irreversible step in the handoff notes.

Run `node "<skill>/scripts/read-task.mjs" "<task.html>"` and applicable display checks, then post ready with the current expected_session_id/expected_revision/job_id. On failure, retain frozen answers, post failed with a concise human-readable error, and retry under the new job. Never put raw SSE events, JSON payloads or traces into a status/error field.

Record real submit-to-next-question and save-to-document timings in test evidence. Controlled 168/420-second UI waits and assembly milliseconds are not real model-generation speed.
