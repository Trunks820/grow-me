# Progressive writer handoff

The current conversation applies project-requirement-writer when installed, otherwise the bundled [writer guide](writer-guide.md); the local helper does not call a model. For a **new** document, reuse `assets/writer-shell.html`, copied from the shared writer template, with its three tabs, semantic body, offline reading and task-package behavior. For an existing maintained task page, preserve that page and history; use a validated preview sibling for early reading and atomically update the original page for final delivery.

## Prepare rules before offering save

During question drafting, use answers and existing context only; put unverified facts on a pending-verification list. While the user is answering the expected final round, use the heartbeat-protected, timed `work.mjs --final-round -- <command>` entry described in [runtime](runtime.md#集中查代码) to investigate code, resolve that list, and prepare chapter structure. When no substantive question remains, before `offer` read the installed project-requirement-writer (or `references/writer-guide.md`), this guide, and `assets/writer-shell.html` structure. That pre-read covers rules/templates only. Never infer unsubmitted answers. After save, claim and write directly from the frozen answers; **do not start another code investigation**. If preparation was interrupted, report unchecked facts as risks. A changed frozen answer overrides all preparation and inferred code mappings.

Every newly authored question, including first-round roots, supplies optional-v2 `chapter_id`: the root question ID (a root names itself). Other questions name a root reachable through their dependencies. This document membership does not change `depends_on`, review or tree geometry. Old v2 questions without the field retain the original primary-root projection; v1 is unchanged and read-only. `/context` exposes the resolved ID, and frozen `/document/status.source.chapters[].node_ids` gives the exact membership for writing. Use explicit assignments directly, rather than reverse-engineering chapter membership at save time.

## Write and publish one chapter at a time

After claiming, save `/document/status` in the workspace as `status.json`. Share a short ID contract among the three views: the same requirement IDs, work/criterion IDs, dependencies, chapter anchors and confirmed decisions. These are transient generation inputs; tree.json remains the only interview state. Avoid reprinting full tree/history or template code in every task.

Each part is a UTF-8 JSON file in a workspace generation directory:

```json
{
  "source": {"session_id":"from status", "revision":6, "digest":"from status", "job_id":"from status"},
  "view":"chapter",
  "chapter_id":"root node id",
  "title":"A readable topic name",
  "html":"<p>Actual writer-authored chapter body, with source answers and references.</p>"
}
```

- One `view:chapter` per supplied root ID, generated by `render-chapter.mjs` below. The assembler supplies its exact anchor and readiness flag. AI writes explanatory prose and cross-topic references only; it must not manually copy, paraphrase or invent text labeled as user original answers.
- One `view:design` with the remaining shared design/requirement/constraint HTML; optional title, summary, decisions, updated. Canonical requirement entries keep stable `data-kind="requirement"` IDs.
- One `view:plan` with the development checklist and `data-kind="work"` entries and their requirement/criterion links.
- One `view:acceptance` with `data-kind="criterion"` entries, source requirements, observable checks and truthful `data-field="status"` values.

The three shared views can be authored independently using the common ID contract. Topic chapters are sequential: write one complete chapter, publish it successfully, then write the next. Use parallel agents only when authorized; parallel assembly support does not itself promise lower model latency or permit batching completed chapters.

Start `check.mjs --heartbeat` before writing and stop that heartbeat at the end. For **each** chapter, write only its explanatory HTML to a file outside the parts directory, then run:

```text
node <skill>/scripts/render-chapter.mjs --context <status.json> --tree <frozen-tree.json> --chapter <root-id> --explanation <chapter-prose.html> --out <parts-dir/chapter-id.json>
```

The script validates complete/answered state, session/revision/digest/job and exact chapter membership. It renders question text, **only actually selected** option labels, and exact original free text (escaped HTML with preserved whitespace) straight from the frozen tree. Unselected recommendations never become answers. It adds a separate “方案说明（AI）” section for the prose. Old v2 without chapter_id still uses the existing root projection; explicit membership is honored. Retry with a new job requires regenerating source-bound parts. Keep raw answers out of AI-authored explanatory text; inferred implications must be labeled, not attributed to the user.

**Mandatory: immediately after each chapter is written, run this command and confirm publication before writing the next chapter. Never accumulate several chapters for a single preview publication.** Keep already published parts in the directory; the new chapter is the only newly published one:

```text
node <skill>/scripts/compose-document.mjs --context <status.json> --tree <tree.json> --parts <parts-dir> --preview --url <local-url>
```

This atomically writes `<document_file>.preview.html`, validates the completed chapters against source/revision/digest/job and publishes each one. Missing views/links are visibly pending in the preview, never passing acceptance. A corresponding fruit becomes readable immediately; other fruit stays labeled “生成中”. Source-stale or duplicate parts fail without replacing the final HTML. File names are arbitrary; use distinct names on case-insensitive filesystems.

`--url` is needed for actual publication: without it the command only writes a local preview and records no publication time. Successful publication returns `newly_published_chapters`, `chapter_timings` and `chapter_timing_file`. The service records the first accepted timestamp per chapter and job; re-publishing a chapter preserves it. Two or more newly published chapters in one invocation emit an explicit warning on stderr (also in successful JSON output), without failing the command. An existing published chapter plus one new chapter is not a batch violation. See [verification](verification.md#逐章发布时间) for the permanent timing log and how to read it.

Use `/document/control` action `progress` with the current expected_session_id/expected_revision/job_id and stage `drafting`, `design`, `plan`, `acceptance` or `checking` as real work starts. The timer is elapsed time, not an estimated percentage. Avoid repeated stage-only calls while nothing changes.

Once all pieces are ready:

```text
node <skill>/scripts/compose-document.mjs --context <status.json> --tree <tree.json> --parts <parts-dir>
```

The assembler checks source binding, unique IDs, three views, all chapters and local links and atomically replaces the configured final HTML. It does **not** post ready: run the bundled `scripts/validate_task.py`, `scripts/read_task.py` and applicable display checks, then post ready with the current expected_session_id/expected_revision/job_id. HTML validation confirms structure/source, not user acceptance or implementation approval. On failure, retain frozen answers, post failed with a concise human-readable error, and retry under the new job. Never put raw SSE events, JSON payloads or traces into a status/error field.

Record real submit-to-next-question and save-to-document timings in test evidence. Controlled 168/420-second UI waits and assembly milliseconds are not real model-generation speed.
